Root cause: Accept-Language negotiation treated a path as non-explicit when the first segment was a supported language but not in `SITE_LANGS`. The middleware then prepended the negotiated language, producing paths like `/zh/ja/...` and 404s.

Fixes and refactor:
1. Explicit language prefix detection — Updated `getExplicitLangFromPath` in `src/index.ts` so it only checks `isSupportedLang(seg)` (no longer requires the segment to be in `SITE_LANGS`). Explicit URLs such as `/ja/...` are no longer wrongly redirected to `/zh/ja/...`.
2. Render language from the path — When the path has a supported language prefix, tool routes render in that language even if it is not listed in `SITE_LANGS`.
3. Shared language helpers — Extracted negotiation/helpers into `src/site/lang.ts` (`DEFAULT_LANGS`, `getEnabledLangs`, `getFallbackLang`, `getDefaultLang`, `parseAcceptLanguage`, `pickLang`, `getExplicitLangFromPath`, `withLangPrefix`, `getLangFromPath`, `stripLangPrefix`, `langAlternatesForPath`).
4. Markdown tool language switcher — Updated `src/pages/markdownToHtmlPage.ts` so the language dropdown and alternate links use full `supportedLangs` (all 10 locales).
5. Tool route registrar — Added `src/site/toolRegistrar.ts` exporting `registerToolPage(app, toolName, renderFn)`, which registers `/tools/<name>` and `/:lang/tools/<name>` with shared language logic. Migrated `website-headers` and `markdown-to-html` to this registrar.
