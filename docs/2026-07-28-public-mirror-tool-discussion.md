## 0.1 「每个镜像」的粒度定义（已建议默认）

讨论里说的「做一个镜像 / 每个镜像」，容易混成三种完全不同的东西。此处先定词，避免 SEO、内容和架构各说各话。

### 三级模型

| 层级 | 名称 | 是什么 | 例子 | 是否称为「一个镜像」 |
|---|---|---|---|---|
| **L-Type** | 镜像类型 / 通道 | 同一类上游协议 + 同一套路由/缓存/限流/文档 | `github-releases`、`github-raw`、`npm-hot` | ✅ **产品与运营粒度** |
| **L-Scope** | 作用域 / 白名单项 | 类型之下允许加速的范围边界 | `owner/repo`、某个 npm scope、某个镜像名 | ⚠️ 叫「白名单项」，不叫独立镜像产品 |
| **L-Object** | 资源对象 | 一次可下载的具体文件/层 | `v1.2.3/app-linux.tar.gz` | ❌ 只是缓存对象，不是「一个镜像」 |

```
一个「镜像」（L-Type）
  └── 多条白名单作用域（L-Scope）
        └── 无数可缓存文件（L-Object）
```

### 三种粒度怎么选

| 方案 | 含义 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **按单个资源** | 每个文件/每个 release asset 算「一个镜像」 | 控制极细 | SEO 会爆炸；运营不可规模化；用户心智碎 | ❌ 否决作为产品粒度 |
| **按仓库/包名** | 每个 `owner/repo` 或每个 npm 包算「一个镜像」 | 白名单好讲 | 指南页会变成成百上千薄页；架构上仍是同一套代理 | ⚠️ 适合做 **白名单行**，不适合做产品单元 |
| **按资源类型** | 每种上游形态算「一个镜像」 | 与搜索意图、文档、Worker 路由一致；可分期上线 | 单类型内部仍要用白名单收口 | ✅ **默认采用** |

### 正式定义（建议写入对外文案与内部规格）

> **镜像（Mirror）** = 面向某一类上游资源的只读加速通道。  
> 通道内通过 **白名单作用域** 限制可访问范围；具体文件仅为通道上的 **缓存对象**，不单独立项、不单独做 SEO 落地页。

第一期因此只有 **1 个镜像产品**：

| Mirror ID | 类型 | 作用域粒度 | 对象示例 |
|---|---|---|---|
| `github-releases` | GitHub Release / codeload 下载 | `owner/repo` 白名单 | `/releases/download/...` 文件 |

后续每加一类才算「新开一个镜像」，例如：

| Mirror ID | 何时算新镜像 |
|---|---|
| `github-raw` | 上游域名/路径规则、缓存策略、文档意图与 Release 明显不同时 |
| `npm-hot` | 新的 registry 协议与滥用面，需独立指南与限额 |
| `pypi-hot` / `docker-base` | 同上，各自独立为一个类型 |

**反例（不要这样拆）**:
- ❌「kubectl 镜像」「terraform 镜像」「某 app v1.0.1 镜像」——这些是白名单里的仓库或缓存对象  
- ❌ 为每个 repo / 每个资源做可索引落地页（含所谓 Information Gain 资源页）——**已明确抛弃**；repo 列表集中在 `/allowlist`

### 对三方面的直接约束

| 方面 | 约束 |
|---|---|
| **SEO** | 1 个 Mirror ID ≈ 1 组可索引指南（可加 FAQ/排障）；`/allowlist` 列作用域；代理对象 URL 全部 noindex；**不做**按资源/仓库拆分的 SEO 落地页 |
| **内容** | 文案说「我们提供 GitHub Releases 公益镜像」，不说「我们镜像了 28 个软件」；不按资源批量产说明页 |
| **架构** | 1 个 Mirror ID ≈ 1 组路由前缀 + 1 套校验/缓存/限流策略；白名单是该策略的配置，不是新 Worker、也不是新落地页 |

### 粒度待确认（若推翻默认）

1. 是否接受：**产品按类型，风控按仓库，存储按文件**？  
2. `codeload` 是并入 `github-releases` 同一镜像，还是拆成第二个类型？（建议 **P0 合并**，同一白名单、文档一章说明差异即可）  
3. 将来 npm 是「一个 `npm-hot` 镜像」还是按包名拆产品页？（建议仍 **一个类型 + 热门包白名单**，**不**按包名做 SEO 页）

## 1. 如何做 SEO

### 1.1 SEO 定位：两套意图，不要抢同一套词

```
主站 onlinefreetools.org
  → 意图：在线计算 / 转换 / 检查（tool use）
  → 例子：markdown to html, check website headers, what is my ip

镜像 mirror.onlinefreetools.org
  → 意图：下载加速 / 镜像 / 代理配置（download & mirror）
  → 例子：github release 加速, github 镜像, raw.githubusercontent 慢
```

**原则**:
- 镜像页 **不要** 用主站工具名做主关键词（避免自相残杀）
- 镜像页 **可以** 在正文末尾相关推荐主站工具（内链/跨域链，锚文本自然）
- 主站开发者工具页 **可以** 反链镜像（「下载慢可用公益加速」）形成闭环

用现有三维模型粗评（见工具 SEO 战略 §2.1）：

| 维度 | 镜像说明页 | 评分直觉 |
|---|---|---|
| 搜索意图明确度 | 「github 加速 / release 镜像」意图清晰 | 4–5 |
| 信息增益空间 | 可写用法、限流、延迟对比、自建对比、排障 | 4–5 |
| 主题集群协同度 | 与 Header / IP / Markdown 开发者簇协同 | 3–4 |
| **合计** | | **宜立项说明站 + 窄谱代理；不宜一上来做全量 registry** |

### 1.2 目标关键词簇（讨论稿）

#### A. 核心簇（中文优先冷启动，英文同步占位）

| 意图 | 中文例 | 英文例 | 落地页类型 |
|---|---|---|---|
| 品牌+功能 | onlinefreetools 镜像 / github 加速 | onlinefreetools github mirror | 镜像首页 |
| 场景 | github release 下载慢 | github releases download slow | 场景说明 + 用法 |
| 对象 | raw.githubusercontent 加速 | raw githubusercontent proxy | 路径/对象说明 |
| 对比 | github 镜像站 推荐 | github mirror china | 对比文（中立、可验证） |
| 排障 | curl github timeout | git clone timeout proxy | FAQ / 排障文 |

#### B. 谨慎簇（易引发滥用或 ToS 风险，内容可写、服务慎开）

- npm / PyPI / Docker Hub「全量镜像」类大词：流量大、成本高、易被扫；SEO 可后期再做专题，**服务层第一期不做**
- 「免费代理」「任意 URL 代理」：索引与产品都 **禁止**（开放代理风险）

#### C. 导流桥接词（写在镜像页，链回主站）

| 镜像语境 | 链到主站工具 | 锚文本示例（自然） |
|---|---|---|
| 测节点 / 看 CF 头 | Website Headers | 检查响应头与缓存头 |
| 确认出口 IP | Public IP | 查看当前公网 IP |
| 说明文档转换 | Markdown→HTML | 将 README 转为 HTML |

### 1.3 页面类型与索引策略

| 页面 | URL 示意 | index? | 作用 |
|---|---|---|---|
| 镜像首页 | `mirror.../` | ✅ | 品牌 + 能力边界 + 快速开始 |
| 用法指南 | `mirror.../guides/github-releases` | ✅ | 长尾 SEO + 信息增益（**类型级**，非按资源） |
| 状态页 | `mirror.../status` | ✅ 或弱推 | Trust、E-E-A-T、可引用资产 |
| 白名单目录 | `mirror.../allowlist` | ✅ | 透明公益、可外链（列表页，非一库一页） |
| 政策/ToS | `mirror.../terms` | ✅ | 合规、免责 |
| 实际下载代理路径 | `mirror.../gh/...` 或 ` /proxy/...` | ❌ **noindex** | 纯功能端点，防薄内容海量 URL |
| 按资源/仓库的说明页 | （不建） | — | **已抛弃**，不做可索引资源落地页 |
| 错误/限流页 | 动态 | ❌ | 无 SEO 价值 |

**关键技术 SEO 决策（待拍板）**:

1. **代理 URL 一律 `X-Robots-Tag: noindex`**，并在 `robots.txt` Disallow 代理前缀，避免数百万路径被爬。  
2. **可索引的只有「人文档页」**（首页、类型指南、状态、白名单、政策）。  
3. **Sitemap**：镜像站点单独 `sitemap.xml`，只含人文档；主站 sitemap **不** 收录代理 URL。  
4. **Canonical**：指南页指向自身 apex 子域；勿把镜像指南 canonical 到主站工具页。  
5. **hreflang**：第一期可只做 `zh` + `en`（与主站 10 语种不同；镜像先深后广）。  
6. **Schema**：指南页用 `TechArticle` / `HowTo` + `FAQPage`；状态页可用 `WebApplication`（如实描述，禁止假评分）。  
7. **出站链接**：指向 GitHub 官方文档、Cloudflare 文档时用正常出站；付费/交换不做（见外链策略）。

### 1.4 与主站的链接与权重关系

```
主站 /zh/tools/website-headers  ←→  镜像 /guides/github-releases
主站 /devlogs/镜像搭建日志      ←→  镜像 /status、/terms
```

| 做法 | 建议 | 原因 |
|---|---|---|
| 镜像→主站工具 | 每页 1–3 条相关推荐，`dofollow` 可接受（同品牌） | 导流 + 主题关联 |
| 主站→镜像 | 仅开发者相关工具与 devlogs | 避免计算器页硬塞镜像 |
| 把镜像当外链农场 | ❌ | 违反「为人写作」，且无长期价值 |
| 镜像页堆砌「免费在线工具」主站词 | ❌ | 意图错配、自相竞争 |

### 1.5 内容质量与 Google 政策对齐

对齐 [工具 SEO 战略](./2026-07-09-tool-seo-strategy.md) 与 People-First：

- **必须有真实功能**：能下载/加速，而不是空壳「镜像介绍站」  
- **必须写清边界**：白名单、限速、非官方、可能与上游不一致  
- **禁止**：批量 AI 生成无审核的「全国镜像站大全」薄内容页  
- **禁止**：按资源/仓库批量产可索引说明页（含以 Information Gain 为名的一资源一页）  
- **dateModified**：仅在用法、白名单、架构有实质变更时更新  
- **YMYL**：镜像偏工具基础设施，仍需安全与滥用说明，不给违法用途建议

### 1.6 SEO 成功指标（讨论用 KPI）

| 指标 | 3 个月 | 6–12 个月 |
|---|---|---|
| 镜像人文档收录数 | 5–15 | 20–40 |

| 镜像→主站点击率 | ≥2% | ≥3–5% |

1. 镜像品牌名：继续用「Online Free Tools Mirror」还是独立短名？  
2. 第一期语言：仅中英，还是直接复用主站 10 语种（成本高）？

## 2. 做哪些内容

### 2.1 内容分层模型

```
L0  服务能力（能用）     ← GitHub Release 白名单代理等
L1  使用说明（会用）     ← 指南、命令示例、配置片段
L2  信任透明（敢用）     ← 状态、白名单、限流、成本与 ToS
L3  教育导流（愿点）     ← 与 Header/IP/Markdown 相关的教学块
L4  叙事传播（愿分享）   ← devlogs、架构图、延迟对比实验
```

公益站缺 L2/L4 会被当成灰产代理；导流缺 L3 则只有流量没有转化。

### 2.2 P0 内容清单（建议第一期必做）

#### A. 服务侧（最小可用）

| 项目 | 说明 | 备注 |
|---|---|---|
| GitHub Release 文件代理 | 仅 `GET/HEAD`，白名单 owner/repo | 最高频痛点 |
| 可选：codeload 源码包 | 同白名单 | 注意大文件与 Range |
| 健康检查 | `/health` 或状态 API | 供监控与状态页 |

**明确不做（P0）**: 任意 URL 反代、POST 写操作、Docker 全量、npm/PyPI 全量、HF 模型全量、**按资源/仓库的可索引 SEO 落地页**。

#### B. 可索引文档页

| 页面 | 核心内容模块 |
|---|---|
| **首页** | 一句话定位、快速开始、能力边界、链到指南/状态/主站 |
| **GitHub Releases 指南** | 适用场景、复制即用 URL/命令、限制、排障、相关工具 |
| **白名单页** | 当前允许的仓库列表、申请方式（若有）、更新日志 |
| **状态页** | 延迟探测、缓存命中、今日流量、维护公告 |
| **使用条款** | 非官方、滥用禁止、日志保留、免责、联系方式 |

#### C. 主站联动内容

| 内容 | 位置 | 目的 |
|---|---|---|
| 一篇以上 `devlogs` | `/devlogs/` | 公益叙事 + SEO + 外链资产 |
| Headers / IP 工具页「相关」块 | 主站工具页底部 | 闭环导流 |
| 镜像页「相关工具」块 | 镜像指南页底部 | 导流 |

### 2.3 P1 / P2 内容（讨论扩展）

| 优先级 | 内容 | 条件 |
|---|---|---|
| P1 | raw.githubusercontent 文本/小文件加速 | P0 稳定、滥用可控 |
| P1 | 一篇「如何选择镜像 vs 自建 Workers」对比文 | 有真实自测数据 |
| P1 | npm 或 PyPI **热门包**按需缓存专题（单一生态） | 账单与 ToS 评估通过 |
| P2 | Docker 超热基础镜像层 | 存储与扫描防护就绪 |
| P2 | 多语言指南扩到 es/ja 等 | 中英指南数据验证有效后 |
| 暂缓 | 「镜像大全」目录型薄页 | SEO 风险高、信息增益低 |
| **已抛弃** | 一资源/一仓库可索引说明页（含 IG 深页方案） | 不再作为内容方向 |

### 2.4 单页信息架构（指南页模板）

建议每个**类型级**指南页固定结构（与主站教育式风格一致）：

```
H1  场景化标题（如「GitHub Release 公益加速」）
├─ 一段：解决什么问题 / 不解决什么问题
├─ 快速开始（命令或 URL 模板）     ← 首屏完成任务
├─ 工作原理（简图：用户 → CF Edge → 源站/R2）
├─ 限制与公平使用（限速、白名单、大小）
├─ 排障 FAQ（超时、403、429、校验失败）
├─ 透明数据（链到 /status、/allowlist）
├─ 相关 Online Free Tools（1–3 个）
└─ 参考链接（GitHub 官方、Cloudflare Docs）
```

**导流文案原则（讨论约定）**:
- 先完成用户任务，再出现工具推荐  
- 禁止全屏弹窗、强制关注、下载前验证码式导流  
- 推荐理由须与场景相关（例如「下载后可用 Markdown 工具预览 README」）

### 2.5 公益叙事与信任文案要点

页面上应可被用户与爬虫同时读到的事实：

1. **非官方** — 与 GitHub / npm 等无隶属关系  
2. **只读** — 仅缓存/代理允许的 GET 资源  
3. **公平使用** — 公开限额，防止一家吃光带宽  
4. **可验证** — 白名单与状态公开  
5. **可关停** — 成本或滥用超标时缩小范围，并在状态页公告  

devlogs 建议选题：
- 为什么做公益镜像、为什么不用开放代理  
- Cloudflare Workers + Cache / R2 选型记录

## 3. 架构怎么搭设

### 3.1 设计目标

| 目标 | 含义 |
|---|---|
| 低延迟 | 边缘命中优先，减少跨境回源 |
| 低风险 | 非开放代理；默认拒绝未白名单路径 |
| 低耦合 | 镜像故障不影响主站工具可用性 |
| 可观测 | 状态页 + 日志/指标可讲清公益运营 |
| 可导流 | 人文档与主站工具互链，功能 API 与文档分离 |

### 3.2 推荐总体架构

```
                    ┌─────────────────────────────────────┐
                    │         Cloudflare Edge             │
  用户 ──────────►  │  DNS: mirror.onlinefreetools.org    │
                    │                                     │
                    │  ┌─────────────┐  ┌──────────────┐  │
                    │  │ Pages/静态  │  │ Worker       │  │
                    │  │ 人文档站点  │  │ 代理 + 缓存  │  │
                    │  │ / /guides   │  │ /gh/* /api/* │  │
                    │  └──────┬──────┘  └───────┬──────┘  │
                    │         │                 │         │
                    │         │          ┌──────▼──────┐  │
                    │         │          │ Cache API   │  │
                    │         │          │ (热文件)    │  │
                    │         │          └──────┬──────┘  │
                    │         │                 │ miss    │
                    │         │          ┌──────▼──────┐  │
                    │         │          │ 上游 GitHub │  │
                    │         │          └──────┬──────┘  │
                    │         │          ┌──────▼──────┐  │
                    │         │          │ R2（可选）  │  │
                    │         │          │ 超热回填    │  │
                    │         └──────────┴─────────────┘  │
                    └─────────────────────────────────────┘
                                      │
                    导流链接 ──────────► onlinefreetools.org（现有 Workers 主站）
```

**为何文档与代理拆开**:
- 文档可强缓存、可索引、变更少  
- 代理要限流、要 noindex、要隔离爆破流量  
- 主站保持现有工具部署，不被镜像流量拖垮

### 3.3 组件职责

| 组件 | 职责 | 实现备选 |
|---|---|---|
| 人文档站点 | 首页/指南/条款/白名单展示 | Cloudflare Pages 或主仓静态路由子域 |
| Mirror Worker | 校验白名单、代理、缓存、限流、安全头 | 独立 Worker 项目（推荐） |
| Cache API | 边缘缓存 Release 资产 | Worker `caches.default` |
| R2（P1） | 超热文件真镜像，源站不稳时仍可用 | 按需回填，不预同步全库 |
| KV / D1（可选） | 白名单配置、限额计数、公告文案 | KV 适合配置；计数可用 Cache 或 Durable Object |
| 主站 | 工具 + devlogs + 反向入口 | 现有 Hono Workers 应用 |
| 可观测 | 状态页数据、告警 | Worker 指标 + 定时探测 |

### 3.4 路由草案

```
# 人文档（可索引）
GET  /                         # 首页
GET  /guides/github-releases   # 类型级指南
GET  /allowlist                # 白名单列表（非一库一页）
GET  /status                   # 状态
GET  /terms                    # 条款
GET  /robots.txt
GET  /sitemap.xml

# 功能 API（noindex）
GET  /health
GET  /gh/:owner/:repo/releases/download/:tag/:file
HEAD 同上
GET  /api/status.json          # 状态页数据

# 拒绝 / 不做
*    /proxy?url=               # 禁止任意 URL
*    /r/:owner/:repo           # 不做按资源 SEO 落地页
*    非白名单 owner/repo       # 403
*    非 GET/HEAD               # 405
```

### 3.5 缓存与一致性策略

| 资源 | 缓存建议 | 说明 |
|---|---|---|
| 带版本 tag 的 Release 文件 | 长 TTL（天～年） | 内容通常不可变 |
| `latest` 类可变路径 | 短 TTL 或不缓存 | 防版本滞后 |
| 人文档 HTML | CDN 缓存 + 发版刷新 | |
| 白名单配置 | KV 近实时；Worker 内存短缓存 | 变更需快速生效 |
| 索引页（若做包源） | 短 TTL | 与 artifact 长缓存分离 |

支持 **HTTP Range**（大文件必需）；缓存键需考虑 Range / 编码，避免错乱。

### 3.6 安全与公平使用（架构硬约束）

```
请求进入
  → 方法仅 GET/HEAD
  → 路径匹配允许模式
  → owner/repo ∈ 白名单
  → IP / CF ASNum 速率限制
  → 单连接/单日配额
  → 文件大小上限
  → 回源超时与重试上限
  → 响应剥离危险头 / 补安全头
  → Cache 命中则不再回源
```

**禁止清单（写入实现与条款）**:
- 开放 URL 代理  
- 跟随跳转到非 GitHub 许可域（防 SSRF 绕法需严格）  
- 把镜像当成通用 CORS 任意源站  
- 记录并公开用户下载的完整文件列表到可索引页（隐私）

### 3.7 与主站导流的技术接点

| 接点 | 实现 |
|---|---|
| 镜像页相关工具 | 静态链接到 `https://onlinefreetools.org/{lang}/tools/...` |
| 主站反链 | i18n article / 相关区块增加镜像指南 URL |
| 状态页小工具 | 「查看本机 IP」「检查镜像响应头」深链到主站工具并预填说明 |
| 统计 | 镜像与主站分物业统计；可用 UTM：`utm_source=mirror&utm_medium=referral` |
| 不共享登录态 | 主站无账号则无需 SSO；保持简单 |

### 3.8 分期落地（建议）

| 阶段 | 时间盒 | 交付 | 退出标准 |
|---|---|---|---|
| **M0 设计** | 本讨论收敛 | 白名单初稿、域名、KPI | 三方面问题有书面结论 |
| **M1 MVP** | ~2–4 周 | 子域 + Worker 白名单代理 + 5 个文档页 + 主站互链 + 1 篇 devlog | 可用性、无开放代理、有首批真实下载 |
| **M2 信任** | +2–4 周 | 状态页自动化、限流仪表、成本周报 | 可公开运营数据 |
| **M3 扩展** | 按数据 | raw 小文件或单一包源热缓存 | 账单可接受且导流率未下降 |

### 3.9 成本与运维假设（讨论用）

- Workers 请求数与回源流量是主成本；应用 Cache/R2 降低回源  
- 被扫描时：收紧白名单 + 更狠限流，而不是扩容硬抗  
- 关停策略：先停代理保留文档与公告，避免「网站消失」损害信任与 SEO

### 3.10 架构待讨论问题

1. 人文档用 **独立 Pages 项目** 还是 **同一 monorepo 另一 Worker 路由**？  
2. 白名单存在 **代码内常量**（简单审计）还是 **KV 可热更新**？  
3. 第一期是否上 R2，还是仅 Cache API？（建议 MVP **不上 R2**）  
4. 日志保留多久？状态页展示哪些聚合指标才不算暴露用户隐私？  
5. 是否与主站共用 Cloudflare 账号/账单告警阈值？

## 4. 三方面交叉决策表（开会用）

| 决策项 | SEO 影响 | 内容影响 | 架构影响 | 建议默认 |
|---|---|---|---|---|
| 子域 `mirror.` | 意图分离清晰 | 需独立 IA | DNS + 独立 Worker | ✅ 采用 |
| 代理 URL noindex | 避免薄内容爆炸 | 人文档承担收录 | robots + 响应头 | ✅ 采用 |
| 仅 GitHub 白名单 | 词簇更窄但可深 | 指南更易写透 | 实现简单、风险低 | ✅ P0 |
| 中英双语 | 覆盖主要搜索 | 翻译量可控 | i18n 子集 | ✅ P0 |
| 开放申请加白 | 可能带来 UGC/spam | 运营文案增加 | 审核流程 | ⚠️ 默认关闭 |
| npm 全量镜像 | 大词流量诱惑大 | 内容易空泛 | 成本与 ToS 高 | ❌ 不做 |
| 强弹窗导流 | 短期点击↑长期信任↓ | 违背公益定位 | 前端拦截 | ❌ 禁止 |
| 一资源一 SEO 页（含 IG 深页） | 长尾诱惑大、薄内容/维护风险高 | 按资源产页成本高 | 多落地页路由 | ❌ **已抛弃** |
